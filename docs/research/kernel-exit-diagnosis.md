日期：2026-10-11（Asia/Shanghai）。初始处置：恢复官方 1.19.29，保留用户级 systemd 监督及稳定出口。后续已通过监督器启用实验试用，见文末的最新状态。

## 历史证据的限制

## 反馈循环与对照

验收命令：

```bash
python3 tests/integration/live_tls_acceptance.py \
  --root "$HOME/.config/mihomo" --expected-version 1.19.29 \
  --url https://chatgpt.com/robots.txt --requests 3
```

该命令验证真实 ChatGPT TLS/HTTP 响应及同一进程持续可用；进程消失、端口失效或被另一实例占用、HTTP 状态不符、证书错误或传输未完成均失败。公开首页的初次基线为 HTTP 403、TLS 证书有效、进程正常，与进程消失是不同现象；公开 robots.txt 的稳定基线为连续三次 HTTP 200。

对照假设和预测：

1. 执行会话清理：普通后台启动的官方和实验内核都会在执行会话结束后消失；独立 systemd 托管的实例不会表现相同故障。
2. 实验内核业务故障：只有实验版在真实请求后退出，独立监督下也应能够复现并取得退出状态。
3. OOM 或外部终止：需要系统日志、cgroup 内存事件或监督进程取得的退出信号支持。

测试由独立临时 systemd 服务保障恢复，先停止正式 proxy-mihomo.service，再运行配置副本。正式版本选择及配置文件不变；临时服务正常结束和异常停止后均尝试恢复正式服务。所有含节点、认证或完整日志的文件只保存到本机私密诊断目录。

| 场景 | 真实 ChatGPT TLS | 进程结果 |
| --- | --- | --- |
| systemd 管理的官方 1.19.29 | 连续三次 200 | 稳定基线通过 |
| 独立 systemd 托管实验版，原配置 | 连续三次 200 | 观察期内存活，无意外退出 |
| 独立 systemd 托管实验版，自适应配置 | 连续三次 200 | 观察期内存活，无意外退出 |
| 实验版先健康，再主动终止 | 先有一次 200 | 验收失败，捕获 PID/端口失效 |
| 工具会话内 `proxy start`，官方版 | 启动时一次 200 | 会话结束后进程消失，独立观察器捕获 |
| 工具会话内 `proxy start`，实验版、原配置 | 启动时一次 200 | 会话结束后进程消失，独立观察器捕获 |
| 恢复官方服务后 | 连续三次 200 | 原配置未改变，服务 active |

两个普通后台启动的内核都留在执行会话的 cgroup/进程组中；300 秒的 nohup sleep 对照也在约 8 秒内消失。记录支持执行会话回收这一解释，不能把该现象归因于实验内核特有崩溃。实际历史终止信号仍未知，其他尚未复现的内核问题未被排除。第一轮分开准备/启动的观察器因等待超时而恢复了正式服务，该轮不计入有效对照；后续将准备和启动放入同一次调用，避免该竞争。

## 修改与适用范围

切换说明改为先停止 systemd 服务，版本启用后通过 systemd 启动；验收放到启动命令完成后的独立调用中。`live_tls_acceptance.py` 持续检查 PID 身份、版本、两个端口及真实 HTTPS 响应；Linux 检查端口所有者。真实终止注入验证能识别“启动健康、请求成功、随后进程消失”，两个实际 socket 回归测试验证竞争进程的监听不能借用为候选健康证据。

此记录没有把历史故障标为已彻底修复，也不证明实验版适合长期运行。公开 HTTPS 请求不等同于经过认证的 Codex/Antigravity AI 请求；机器人文本的短时完整传输不等同于长连接稳定性。实验版继续停用，当前稳定服务及已知可用出口保留。后续真实业务试用必须使用长期监督、独立验收及停机回退；不能再凭 PID 和控制器就绪宣告切换成功。

## 现有 CLI 入口接入监督器

后续将 proxy start/stop/restart 接到已有、且 PIDFile 匹配当前配置目录的用户级服务。先向 systemd 派发，再由服务内部取得启动锁，避免外部调用持锁等待自己的 ExecStart；通过 cgroup 判断内部工作进程，避免递归。没有匹配服务则沿用独立生命周期；已安装监督器不可达或派发失败时拒绝另起实例。用户服务文件没有被修改。

真实验证：proxy stop 后等待三秒服务仍保持停止；proxy start/restart 返回后，在独立工具调用中确认进程属于用户服务并仍存活。四次 chatgpt.com/robots.txt 请求复用同一 TLS 1.3 socket，每次之间空闲十秒，均完整返回 200；Google/Gemini 的公开 HTTPS 基线也均为 200。新增四个监督器边界测试（包括派发失败不启动第二个内核），管理层共 28 项测试通过。数据见 supervised-lifecycle-results.json。公开短时重复 GET 不是经过认证的 AI/SSE 业务。

## 监督下的本机试用

启动入口修复及 28 项测试通过后，重新根据当前配置生成候选。初始地区偏好设为当前已知稳定出口所在的 US；地区根据用户节点标签判断，不验证实际地理位置。候选通过隔离配置校验后，由独立临时 systemd 服务执行停止原服务、明确启用固定实验版本、通过现有用户服务启动，再分别执行真实 HTTPS 验收。异常退出的 ExecStopPost 有独立恢复路径，检查本次候选标识后回退，避免改动另一操作选择的版本。

ChatGPT、Google、Gemini 的公开 HTTPS 请求全部返回 200。ChatGPT 四次 GET 复用同一 TLS 1.3 socket，请求间空闲十秒；响应完整、证书有效，主进程未更换，服务重启次数为 0。临时验收服务已完成退出，核心继续由原 proxy-mihomo.service 管理。当前运行 v1.19.32-adaptive-prototype.2，上一版 1.19.29 及原配置/缓存保留供停机回退。原用户服务文件未修改。数据见 supervised-trial-results.json。
